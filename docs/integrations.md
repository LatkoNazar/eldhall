# Конфігурація знань, навичок та інтеграцій

Станом на **31 жовтня 2026 року**. Цільовий дизайн перед реалізацією;
цей документ не описує наявні команди, готову схему конфігурації чи виконані перевірки.
Бізнес-модель і розгортання визначено в [business-model.md](business-model.md).

## П’ять складових конфігурації

| Складова | Призначення | Межа довіри |
| --- | --- | --- |
| `docs` | Вихідні матеріали: файли, дозволені URL, документи, завантажені через API | Дані для відповіді, а не інструкції чи дозволи |
| `knowledge` | Індексація та пошук по доступних документах із посиланнями на джерела | Вибірка обмежена організацією, проєктом і правами суб’єкта |
| `skills` | Перевірені та версійовані Markdown-інструкції й сценарії роботи агента | Визначають поведінку в межах уже наданих повноважень |
| `mcp` | Підключення бізнес-інструментів через MCP або конфігуровані адаптери | Кожен виклик перевіряється backend та цільовою системою |
| `guards` | Додаткові політики, перевірки входу/виходу, ліміти та погодження дій | Доповнюють обов’язковий контроль доступу |

Складові підключаються окремо для організації та проєкту. Бот із базою знань може працювати
без MCP. Відсутність dashboard не змінює способу налаштування жодної складової.
Відсутність `guards` не вимикає базову авторизацію, ізоляцію чи перевірку власника даних.

`docs` зберігає джерела; `knowledge` створює їхній пошуковий індекс і повертає фрагменти
з походженням. Для локального режиму потрібні локальні embeddings; індексування та пошук
використовують сумісну embedding-модель. Зміна моделі потребує переіндексації.
Завантажений документ не може оголосити себе skill, змінити політику чи додати інструмент.
Skills активує уповноважений адміністратор після перевірки версії та змісту.

## Вбудовані та власні support-skills

У цільовому продукті агент спеціалізується на клієнтській, технічній та внутрішній підтримці.
Базовий `support`-preset має постачатися з версією релізу й містити такі навички:

- класифікувати звернення та уточнювати відсутню інформацію;
- відповідати за доступною базою знань із посиланнями на джерела;
- діагностувати проблему через дозволені інструменти;
- створювати тикет або передавати оператору стислий підсумок і виконані кроки;
- підтверджувати з користувачем, чи вирішено звернення.

Агент обирає навички за конкретним випадком; перелік вище не задає обов’язкового лінійного workflow.
Адміністратор може увімкнути потрібні вбудовані навички, розширити їх або явно замінити вибрані
через валідовану конфігурацію. Власні навички отримують namespaced ID на кшталт
`custom/order-support`, щоб однакова назва випадково не перевизначила вбудовану навичку.
Заміна має явно вказувати ціль і проходити перевірку; базові guards та дозволи залишаються чинними.

Власні skills — перевірені версійовані Markdown-файли або пакети з `SKILL.md`.
Плануємо додавання через файл чи mount або адміністративний API без перебудови образу застосунку.
Skill не надає нових прав чи інструментів. Якщо потрібної інтеграції немає, агент уточнює
можливий наступний крок або передає звернення оператору, а не вигадує результат її виклику.

## Джерела бізнес-інструментів

Підтримуємо як цільовий дизайн три способи конфігурації адаптерів поряд із зовнішнім MCP:

- **OpenAPI:** обираємо конкретні `operationId` з перевіреної специфікації та описуємо їхні права.
- **REST:** явно задаємо метод, фіксовану адресу, схеми аргументів і результату та credential reference.
- **База даних:** відкриваємо названі параметризовані запити або views через роль із мінімальними правами.

Адаптер перетворює ці операції на визначені інструменти. Повна специфікація API не означає
дозволу на всі операції. Довільний SQL і довільні адреси запитів за замовчуванням недоступні.
Наявний MCP-сервер може підключатися без переписування його бізнес-логіки.

## Приклад майбутнього `support.yaml`

Це **ілюстрація запропонованого контракту**, а не файл, який поточний застосунок уже приймає.
Назви полів, resource paths, адреси й ідентифікатори нижче є прикладами. Credential references
розв’язує backend через environment або secret store; значення секретів у YAML не зберігаються.

```yaml
schemaVersion: proposed/v1
docs:
  sources:
    - id: company-policies
      type: files
      path: ./company-docs
knowledge:
  sources: [company-policies]
  embedding:
    provider: local
    model: example-embedding-model
skills:
  preset: support
  bundles:
    - id: custom/customer-support
      path: ./skills/customer-support.md
      revision: v1
mcp:
  servers:
    - id: crm
      url: https://crm.example.invalid/mcp
      credentialRef: secret:CRM_MCP
      allowTools: [get_order_status]
  adapters:
    - id: store-api
      type: openapi
      spec: ./integrations/store.openapi.yaml
      operations: [createTicket]
      credentialRef: secret:STORE_API
    - id: shipping
      type: rest
      method: GET
      url: https://store.example.invalid/shipping-options
      credentialRef: secret:STORE_API
    - id: orders
      type: database
      queries: [order_summary_v1]
      connectionRef: secret:ORDERS_READONLY
guards:
  policyFile: ./policies/support.yaml
  approvalRequired: [store-api.createTicket]
  toolCallLimit: 8
```

Опис схем REST і визначення названих DB-запитів належать перевіреній конфігурації адаптерів;
модель передає лише дозволені аргументи. Конкретні адреси та параметри embeddings задаються
конфігурацією провайдера під час розгортання, окремо від інструментів бізнес-систем.

## Права та виконання виклику

Backend отримує організацію, проєкт, користувача та його права з перевіреного контексту
автентифікації. Аргументи моделі не можуть підмінити цей контекст. Перед кожним викликом
backend перевіряє право на операцію та доступ до конкретного замовлення, тикета чи документа.
Agent runtime не отримує прямі DB-credentials або адміністративні ключі бізнес-систем.

Allowlist визначає доступні інструменти, але не замінює авторизацію. MCP tool annotations
також не є дозволом. Зовнішній MCP-сервер має забезпечувати потрібну перевірку доступу,
або її явно виконує наш адаптер до виклику; неперевірений виклик не активується.
За замовчуванням доступ закритий, а некоректна конфігурація guards блокує активацію її версії.

Guards детерміновано перевіряють схеми, доступ, ліміти й необхідність погодження до дії;
результат проходить перевірку структури та дозволеного до повернення вмісту.
Це не гарантія повного виявлення prompt injection: текст моделі чи джерела не змінює політику.

Для операцій запису політика може вимагати погодження уповноваженої людини через API
або автентифікований webhook. Воно прив’язується до конкретної операції, точних аргументів,
суб’єкта та строку дії. Після зміни аргументів потрібне нове погодження; повторне виконання
контролюється idempotency key. Dashboard для цього не обов’язковий.

## Налаштування без UI та майбутні критерії готовності

У self-host адміністратор задає файл конфігурації й посилання на секрети. Керування через API
доступне лише адміністративній ролі; bot/customer API не дозволяє змінювати інтеграції чи політики.
Майбутній dashboard редагує той самий валідований контракт. Перед активацією зміни перевіряються
як єдина версія конфігурації; частково перевірена версія не стає активною.

Під час build перевіряємо, що:

1. Без web-контейнера можна підключити джерела, індекс, skill і дозволений бізнес-інструмент.
2. Бот без MCP відповідає з доступних документів і повертає джерела; закриті документи не потрапляють у вибірку.
3. Зміна організації або власника в аргументах не дає доступу до чужих даних; відсутність guards цього не змінює.
4. Skill або документ не можуть розширити повноваження; клієнтський запит не змінює конфігурацію адміністратора.
5. Запис без потрібного погодження не виконується; зміна аргументів, прострочення й повторна доставка обробляються явно.
6. Невідома операція та некоректна конфігурація не отримують доступу через загальний fallback.
7. Support-preset обробляє звернення без власних skills; власний сценарій додається й активується
   через headless-конфігурацію без зміни backend-коду, перебудови образу чи розширення дозволів.
