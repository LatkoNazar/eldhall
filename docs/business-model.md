# Бізнес-модель AI Customer Support

Станом на **31 жовтня 2026 року**. Документ фіксує погоджений напрям продукту перед розробкою.
Це цільова модель, а не опис уже реалізованих можливостей. Поточна `main` містить Python-шаблон;
Node.js-варіант є в гілці `codex/node-backend`. Перехід продукту на TypeScript ще належить виконати.

## Продукт і цінність

Створюємо AI Customer Support із відкритим кодом: сервіс відповідає за матеріалами компанії,
виконує дозволені дії через інтеграції, створює звернення та передає розмову оператору.
Його можна додати до наявного сайту, застосунку, бота або CRM через API.

Агент спеціалізується на підтримці: клієнтській, технічній або внутрішній для команди.
Базова комплектація має містити вбудований набір support-skills, який користувач може
доповнювати власними навичками. Агент добирає навички під звернення та контекст;
одна фіксована послідовність кроків не визначає всі сценарії підтримки.

Початкова аудиторія — команди з власним продуктом або сайтом, яким потрібна підтримка
з контролем даних, вибором AI-провайдера та можливістю самостійного розгортання.
Цінність продукту складається з бази знань, історії звернень, інструментів підтримки та інтеграцій.
Модель і агентний рушій є змінними складовими цієї системи.

## API є основним способом використання

Backend працює без нашого інтерфейсу. Dashboard і чат-віджет — незалежні додаткові компоненти.

| Компонент | Роль | Обов’язковість |
| --- | --- | --- |
| Backend та agent runtime | API, діалоги, база знань, дії, інтеграції | Ядро продукту |
| Web dashboard | Робота операторів, документи, налаштування, статистика | Опційний контейнер |
| Чат-віджет | Готовий чат для вбудовування на сайт | Опційний окремий артефакт |

Початкове налаштування, вибір моделі, імпорт документів, діалоги, тикети й передача оператору
мають бути доступні через API. Параметри запуску та bootstrap задаються конфігураційним файлом
і змінними середовища. Жоден обов’язковий крок не повинен вимагати браузерного onboarding.
Запуск і health/readiness backend не залежать від наявності чи доступності dashboard.

Віджет можна використати без dashboard. Клієнт із власним UI може працювати лише через API.
Dashboard також є клієнтом того самого API, а не окремим джерелом бізнес-правил.

## Конфігуровані складові агента

Для кожної організації та проєкту конфігуруємо п’ять складових: **docs** — вихідні документи,
**knowledge** — пошуковий індекс і retrieval із джерелами, **skills** — перевірені версійовані
сценарії, **mcp** — бізнес-інструменти та адаптери, **guards** — додаткові перевірки й політики дій.
Складові підключаються за потребою; базові авторизація, ізоляція та перевірка власника даних
залишаються обов’язковими. Усі налаштування доступні без dashboard. Детальні межі довіри,
підключення OpenAPI/REST/DB та погодження дій описані в [інтеграціях](integrations.md).

## Два способи отримати продукт

| | Самостійний хостинг | Managed cloud |
| --- | --- | --- |
| Продуктове ядро | Спільна відкрита кодова база | Те саме ядро |
| Розгортання | На інфраструктурі користувача | Ми розгортаємо та експлуатуємо |
| AI | Власні API-ключі або локальні моделі | Власний ключ або тариф із визначеним обсягом AI |
| Дані й резервні копії | Відповідальність користувача | Керована послуга з визначеними умовами |
| Оновлення й моніторинг | Виконує користувач | Забезпечуємо ми |
| Оплата нам | Безкоштовне використання відкритого ядра | Платна послуга хостингу й експлуатації |

Самостійний хостинг може вимагати оплати сервера, GPU або зовнішнього AI-провайдера.
Безкоштовний код не означає безкоштовні обчислення. Cloud продає зручність запуску,
оновлення, резервне копіювання, спостережуваність і підтримку експлуатації.

## Цільовий стек

| Частина | Вибір для старту |
| --- | --- |
| Продуктовий код | TypeScript |
| Backend | Node.js та Fastify |
| Опційний dashboard | React, Vite та TypeScript |
| Дані й пошук у базі знань | PostgreSQL та pgvector |
| Черги й фонові задачі | Redis та BullMQ |
| Перший agent runtime | DeepSeek Harness через TypeScript SDK; вибір runtime погоджено користувачем |
| Перший AI-провайдер | Gemini API з наявним у команди ключем |

Модельний сервер є незалежним сервісом і може використовувати інший стек.
Документи, діалоги, тикети, правила доступу, контракти API та support-tools належать нашому backend.
Стан runtime не замінює продуктову базу даних. Дані пов’язуємо з організацією та проєктом;
доступ, ключі, сесії та події runtime ізолюємо між організаціями для майбутнього cloud.

## Agent runtime і провайдер моделі

За рішенням користувача DeepSeek Harness є першим і типовим runtime. Перевикористовуємо його
agent loop, сесії та механізми skills там, де вони підходять нашим контрактам. Тонкий адаптер
керує lifecycle і подіями; наш core зберігає діалоги, tools/authZ, знання, approvals та audit.
Деталі інтеграції й переносимість runtime state перевіряємо в spike. Harness отримує визначений
набір інструментів підтримки: пошук у документах, читання дозволених даних, створення тикета,
передачу оператору. Розширення цього набору є явною продуктовою інтеграцією.
Другий агентний engine і LangGraph до MVP не входять; власний engine розглядаємо за реальною потребою.
Заміна потребуватиме адаптера, поведінкових тестів і міграції або перебудови session state.

Провайдер обирається окремо: Gemini API, DeepSeek API або власний сумісний endpoint.
Gemini-модель можна використати всередині DeepSeek Harness через `GEMINI_API_KEY`.
Для вибору Gemini-моделі Gemini CLI не потрібний; окремий Gemini runtime до MVP не плануємо.
Документовані можливості SDK і провайдерів наведено в джерелах нижче.

Локальна LLM працює окремим процесом або контейнером. Ваги моделей не включаємо до нашого
серверного образу. Для повністю локального пошуку потрібна також локальна embedding-модель:
провайдери генерації відповідей та embeddings конфігуруються окремо. Індексування й пошук
мають використовувати сумісний векторний простір; зміна embedding-моделі потребує переіндексації.

Сумісність протоколу не гарантує надійного виклику інструментів обраною моделлю.
Підтримку конкретного endpoint підтверджуємо сценарієм із нашими support-tools.
Доступ за підпискою чи OAuth додаємо лише для перевірених провайдерів і сценаріїв;
базовий cloud-доступ плануємо через API. Безлімітний доступ за особистою підпискою не обіцяємо.

## Пакування для самостійного розгортання

Плануємо публікувати версійовані Docker-образи в Docker Hub та готову Compose-конфігурацію.
Наведені назви образів і профілів є робочими позначеннями: namespace, теги та публікація ще не визначені.

| Власний образ | Спосіб запуску |
| --- | --- |
| `support-server` | Окремі сервіси `api` та `worker` з одного образу |
| `support-web` | Опційний dashboard, увімкнений окремим Compose-профілем |

Повний стек включає PostgreSQL і Redis або використовує наявні сумісні сервіси користувача.
Локальний модельний сервер можна підключити за адресою endpoint або додати опційним профілем.
Backend-сервіси можна включити до чужого Compose-проєкту без запуску нашого web-контейнера.
Віджет постачається окремим браузерним пакетом чи bundle і не потребує власного контейнера.
Конфігурація, секрети та постійні дані передаються під час розгортання й зберігаються поза образом.

## Монетизація та витрати

Основне джерело доходу — керований cloud. На старті передбачаємо два способи оплати AI:
користувач надає власний ключ і платить за хостинг, або купує послугу з визначеним обсягом AI.
Точні ціни, одиниці тарифікації, квоти, перевитрати та умови підтримки ще не затверджені.
Перш ніж призначати ціну, вимірюємо витрати на моделі, embeddings, зберігання документів,
фонові задачі та експлуатацію. Модель доходу не ґрунтується на необмеженому AI за фіксовану плату.

Повний SaaS-білінг не є умовою першого MVP. Спочатку підтверджуємо цінність підтримки
та відтворюване розгортання; автоматизацію платежів додаємо після вибору тарифної моделі.

## Відкритий код і ліцензія

Погоджений напрям — відкритий продукт із платним managed cloud. Остаточну ліцензію нашого
коду ще не обрано. Apache-2.0 є початковою рекомендацією; AGPL і fair-code потребують
окремого рішення з урахуванням бажаних правил використання та внесків спільноти.
Цей документ не запроваджує ліцензію й не змінює ліцензії залежностей.

Apache-2.0 дозволяє комерційне використання, тому інші компанії теж можуть пропонувати хостинг.
Якщо оберемо обмеження конкурентного SaaS, описуватимемо таку модель як source-available
або fair-code: заборона певного комерційного використання не відповідає визначенню OSI open source.
DeepSeek Harness має MIT-ліцензію; під час пакування зберігаємо належні повідомлення
про авторство та ліцензії сторонніх компонентів.

## Межі першого MVP та критерії готовності

Перший сценарій: додати документи компанії, отримати відповідь із джерелами,
створити звернення або передати діалог оператору, переглянути історію через API чи dashboard.

Готовність цього сценарію перевіряємо такими умовами:

1. Нове розгортання проходить bootstrap, налаштування моделі та імпорт документів без web-контейнера.
2. Через API створюється діалог, зберігається історія та виконується передача оператору або створення тикета.
3. Відсутність dashboard не перешкоджає роботі backend, worker і перевіркам їхнього стану.
4. Dashboard можна підключити пізніше до тих самих даних; віджет працює незалежно від нього.
5. Gemini та обраний локальний endpoint проходять однаковий зафіксований сценарій підтримки.
   Зміна провайдера не потребує переписування продуктових правил; embeddings перевіряються окремо.
6. Користувач може повторити документоване розгортання з опублікованих образів без збірки вихідного коду.
7. Docs, knowledge, skills, MCP та додаткові guards налаштовуються без UI; bot/customer API не змінює ці політики.
   Перевірки доступу й власника даних діють для кожного інструмента, а потрібні погодження доступні через API/webhook.
8. Вбудований support-preset працює без власних skills; адміністратор може додати й активувати
   власний сценарій без UI, зміни backend-коду чи перебудови образу.

Це критерії для майбутнього build, а не звіт про виконані перевірки. Перед публічним релізом
окремо затверджуємо ліцензію, назви образів, підтримувані моделі та умови cloud-послуги.
